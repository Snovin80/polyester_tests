===== СООБЩЕНИЕ 1 (replace-batch) =====

POST /v1/orders/replace-batch: the user docs (Manage orders) say an in-place amend keeps the Order ID and applies to a Limit order that keeps its price and does not increase its total quantity, and Amend or Replace amends when possible. In practice a replace-batch item that keeps the price and decreases newQtyScaled, or keeps price and quantity unchanged, always returns REPLACED with a new order id; the old order becomes CANCELED with terminalReason ORDER_REPLACED, and GetBatchReplaceStatus also shows REPLACED. AMENDED was never returned. POST /v1/orders/modify with the same decrease returns AMENDED and keeps the id, but modify with unchanged price and quantity also returns REPLACED with a new id. The replace-batch reference defines AMENDED differently, as cancel-only without a successor with replacementOrderId zero, while its own response example shows AMENDED with replacementOrderId equal to oldOrderId. Is this by design, and in which case does replace-batch return AMENDED?

Raw, 2026-09-29 09:56:57 UTC, ETH-USDT limit BUY 0.005 at 1350, request {"symbol":"ETH-USDT","items":[{"orderId":"VZGrRXRUG2m","newQtyScaled":4500}]}, HTTP 200: {"acceptedTsNs":"1790675818109854769","batchRequestId":"FQd8bP8ocBe","status":"ADMITTED","results":[{"actionTaken":"REPLACED","oldOrderId":"VZGrRXRUG2m","replacementOrderId":"FJ2wTecwwgQ","status":"ADMITTED"}],"acceptedCount":1,"acceptedTs":{"seconds":1790675818,"nanos":109854769}}. Then GET /v1/spot/orders/VZGrRXRUG2m: "status":"CANCELED","terminalReason":"ORDER_REPLACED"; GET /v1/spot/orders/FJ2wTecwwgQ: "origQty":"0.0045","price":"1350","status":"WORKING".

POST /v1/orders/replace-batch results: for an unknown orderId and for an order of another pair oldOrderId comes back as 1 (zero id) instead of the orderId from the request, so a rejected item can only be matched by position. For CONFLICT_DUPLICATE_CLIENT_ORDER_ID the rejected item has replacementOrderId equal to oldOrderId, while the reference says zero for a rejection before assignment. Is this by design?

Addition to the modify ticket about an order of another pair: replace-batch behaves the same, an AVAX-USDT order sent with symbol ETH-USDT is rejected with UNKNOWN_SYMBOL.

Attached TP/SL prices are not validated. On ETH-USDT (tick 0.01) newAttachedRisk in replace-batch and attachedRisk in POST /v1/orders accept a takeProfit triggerPrice of 3500.005, and the leg trigger is created with 3500.005; a takeProfit at 1000 on a BUY order at 1350 is accepted as well. A standalone POST /v1/triggers on ETH-USDT with triggerPrice 3500.005 is rejected with PRICE_TICK_SIZE. Is this by design?


POST /v1/orders/replace-batch: в пользовательской документации (Manage orders) сказано, что правка на месте сохраняет Order ID и применяется к лимитному ордеру, у которого цена не меняется и общее количество не растёт, а режим Amend or Replace правит на месте, когда это возможно. На деле пункт replace-batch, который сохраняет цену и уменьшает newQtyScaled или оставляет цену и количество без изменений, всегда даёт REPLACED с новым id ордера; старый ордер становится CANCELED с terminalReason ORDER_REPLACED, GetBatchReplaceStatus тоже показывает REPLACED. AMENDED не пришёл ни разу. POST /v1/orders/modify с тем же уменьшением возвращает AMENDED и сохраняет id, но modify без изменения цены и количества тоже возвращает REPLACED с новым id. Справочник replace-batch определяет AMENDED иначе, как отмену без преемника с нулевым replacementOrderId, а пример ответа на той же странице показывает AMENDED с replacementOrderId, равным oldOrderId. Так задумано, и в каком случае replace-batch возвращает AMENDED?

Сырой ответ, 2026-09-29 09:56:57 UTC, ETH-USDT лимитный BUY 0.005 по 1350, запрос {"symbol":"ETH-USDT","items":[{"orderId":"VZGrRXRUG2m","newQtyScaled":4500}]}, HTTP 200: {"acceptedTsNs":"1790675818109854769","batchRequestId":"FQd8bP8ocBe","status":"ADMITTED","results":[{"actionTaken":"REPLACED","oldOrderId":"VZGrRXRUG2m","replacementOrderId":"FJ2wTecwwgQ","status":"ADMITTED"}],"acceptedCount":1,"acceptedTs":{"seconds":1790675818,"nanos":109854769}}. Затем GET /v1/spot/orders/VZGrRXRUG2m: "status":"CANCELED","terminalReason":"ORDER_REPLACED"; GET /v1/spot/orders/FJ2wTecwwgQ: "origQty":"0.0045","price":"1350","status":"WORKING".

results в POST /v1/orders/replace-batch: для несуществующего orderId и для ордера другой пары oldOrderId приходит как 1 (нулевой id), а не orderId из запроса, поэтому отклонённый пункт можно сопоставить только по позиции. При CONFLICT_DUPLICATE_CLIENT_ORDER_ID у отклонённого пункта replacementOrderId равен oldOrderId, хотя в справочнике для отказа до назначения указан ноль. Так задумано?

Дополнение к тикету про modify и ордер другой пары: replace-batch ведёт себя так же, ордер AVAX-USDT, отправленный с symbol ETH-USDT, отклоняется с UNKNOWN_SYMBOL.

Отдельный POST /v1/triggers на ETH-USDT с triggerPrice 3500.005 отклоняется с PRICE_TICK_SIZE. Так задумано?


===== СООБЩЕНИЕ 2 (триггеры) =====

POST /v1/triggers: clientTriggerId is not marked required on the REST page (the ConnectRPC page says min 1 chars), and without it the API returns 400 VALIDATION_ERROR trigger.client_trigger_id must be at least 1 characters. No maximum length is documented. A clientTriggerId of 64 characters is accepted, 65 or more returns 503 UNAVAILABLE instead of a 400 validation error.

Raw, 2026-09-29 10:01:52 UTC, AVAX-USDT SELL stopLoss, clientTriggerId of 65 characters, HTTP 503: {"type":"https://polyester.dev/problems/unavailable","title":"Service Unavailable","status":503,"detail":"read_decode: read tcp 172.17.0.4:41832->10.20.10.151:9100: read: connection reset by peer","code":"UNAVAILABLE"}

POST /v1/triggers with a clientTriggerId that already exists and a different body (other qty or other triggerPrice) returns a Cloudflare 502 Bad gateway HTML page instead of a JSON error such as CONFLICT_DUPLICATE_CLIENT_TRIGGER_ID; the original trigger stays unchanged. The same clientTriggerId with the same body correctly returns the original trigger. Related to the 502 on parallel DELETE of attached legs I reported earlier, but here it is a single request.

Raw, 2026-09-29 10:02:03 UTC, first request with clientTriggerId tt-dup-9QLxxCcDwWXf1, qty 0.513791, HTTP 200: {"acceptedAt":"2026-09-29T10:02:03.739616808Z","acceptedAtTsNs":"1790676123739616808","triggerId":"ZfhZc1pbB5D","clientTriggerId":"tt-dup-9QLxxCcDwWXf1"}. 10:02:06 UTC, same clientTriggerId, qty 0.613791, HTTP 502, text/html body 6458 bytes, <title>polyester.com | 502: Bad gateway</title>, Cloudflare Ray ID a42a267c9f22181f. 10:02:08 UTC, same clientTriggerId, triggerPrice 9.500, HTTP 502, Ray ID a42a268a9fd7181f. 10:02:09 UTC GET /v1/triggers/ZfhZc1pbB5D: "qty":"0.513791","status":"ARMED".

GET /v1/triggers/id right after a successful POST /v1/triggers returned 404 NOT_FOUND in 3 of 10 attempts (200 after 0.3 s), and GET right after a DELETE that returned CANCELED showed ARMED in 6 of 10 attempts (CANCELED after 1 s). For orders the developer docs say GetOrder briefly waits server-side when an accepted order has not reached the read projection and returns a temporary unavailable error instead of NOT_FOUND. Is the trigger behavior by design?

GET /v1/triggers: the parentOrderId filter is ignored, a real parent id (base58 or numeric), a non-existent id and no filter return the same list; the same filter on ConnectRPC ListTriggers returns exactly the two legs of that parent and rejects a non-existent id. The status filter is documented as TriggerStatus enum names listed as CREATED, ARMED, RUNNING, COMPLETED, CANCELED, FAILED, PAUSED, but status=CANCELED returns 400 INVALID_TRIGGER_STATUS; only the ConnectRPC names such as STATUS_CANCELED work, comma-separated values too.

POST /v1/triggers ladder: postOnly is marked required on the REST page and optional on the ConnectRPC page; a ladder without it is accepted and the level orders are placed without post-only. Is this by design?

Addition to the ticket about scaled prices in the triggers reference: trailingDistanceTicks is described as a delta in 1e-9 quote-unit ticks, but it is parsed as a decimal price, as the developer docs say for REST: up to 9 fractional digits are accepted, 9223372036 is accepted and 9223372037 returns overflow (int64 divided by 1e9), so 1 means 1 USDT. TRAILING_DISTANCE_INVALID was never returned, a trailing distance of 9223372036 on AVAX-USDT at about 11.5 is accepted.


POST /v1/triggers: clientTriggerId на странице REST не помечен обязательным (на странице ConnectRPC указано min 1 chars), и без него API отвечает 400 VALIDATION_ERROR trigger.client_trigger_id must be at least 1 characters. Максимальная длина не указана. clientTriggerId длиной 64 символа принимается, 65 и больше даёт 503 UNAVAILABLE вместо ошибки валидации 400.

Сырой ответ, 2026-09-29 10:01:52 UTC, AVAX-USDT SELL stopLoss, clientTriggerId длиной 65 символов, HTTP 503: {"type":"https://polyester.dev/problems/unavailable","title":"Service Unavailable","status":503,"detail":"read_decode: read tcp 172.17.0.4:41832->10.20.10.151:9100: read: connection reset by peer","code":"UNAVAILABLE"}

POST /v1/triggers с уже существующим clientTriggerId и другим телом (другой qty или другой triggerPrice) возвращает HTML-страницу Cloudflare 502 Bad gateway вместо JSON-ошибки вроде CONFLICT_DUPLICATE_CLIENT_TRIGGER_ID; исходный триггер не меняется. Тот же clientTriggerId с тем же телом правильно возвращает исходный триггер. Родственно 502 при параллельном DELETE привязанных ног, о котором я сообщал ранее, но здесь это одиночный запрос.

Сырые ответы, 2026-09-29 10:02:03 UTC, первый запрос с clientTriggerId tt-dup-9QLxxCcDwWXf1, qty 0.513791, HTTP 200: {"acceptedAt":"2026-09-29T10:02:03.739616808Z","acceptedAtTsNs":"1790676123739616808","triggerId":"ZfhZc1pbB5D","clientTriggerId":"tt-dup-9QLxxCcDwWXf1"}. 10:02:06 UTC, тот же clientTriggerId, qty 0.613791, HTTP 502, тело text/html 6458 байт, <title>polyester.com | 502: Bad gateway</title>, Cloudflare Ray ID a42a267c9f22181f. 10:02:08 UTC, тот же clientTriggerId, triggerPrice 9.500, HTTP 502, Ray ID a42a268a9fd7181f. 10:02:09 UTC GET /v1/triggers/ZfhZc1pbB5D: "qty":"0.513791","status":"ARMED".

GET /v1/triggers/id сразу после успешного POST /v1/triggers вернул 404 NOT_FOUND в 3 из 10 попыток (через 0.3 с — 200), а GET сразу после DELETE, вернувшего CANCELED, показал ARMED в 6 из 10 попыток (через 1 с — CANCELED). Для ордеров в документации для разработчиков сказано, что GetOrder коротко ждёт на сервере, если принятый ордер ещё не дошёл до проекции чтения, и возвращает временную ошибку unavailable вместо NOT_FOUND. Поведение триггеров так задумано?

GET /v1/triggers: фильтр parentOrderId игнорируется, настоящий id родителя (base58 или числом), несуществующий id и запрос без фильтра возвращают один и тот же список; тот же фильтр в ConnectRPC ListTriggers возвращает ровно две ноги этого родителя, а несуществующий id отклоняет. Фильтр status описан как имена TriggerStatus со значениями CREATED, ARMED, RUNNING, COMPLETED, CANCELED, FAILED, PAUSED, но status=CANCELED возвращает 400 INVALID_TRIGGER_STATUS; работают только имена из ConnectRPC, например STATUS_CANCELED, значения через запятую тоже.

POST /v1/triggers ladder: postOnly на странице REST помечен обязательным, а на странице ConnectRPC необязательным; ladder без него принимается, и ордера уровней выставляются без post-only. Так задумано?

Дополнение к тикету про scaled-цены в справочнике триггеров: trailingDistanceTicks описан как дельта в тиках 1e-9 quote-единиц, но читается как десятичная цена, как и сказано про REST в документации для разработчиков: принимается до 9 знаков после точки, 9223372036 принимается, а 9223372037 даёт overflow (int64, делённое на 1e9), то есть 1 означает 1 USDT. TRAILING_DISTANCE_INVALID не пришёл ни разу, трейлинг-дистанция 9223372036 на AVAX-USDT при цене около 11.5 принята.
