POST /v1/orders/replace-batch: the user docs (Manage orders) say an in-place amend keeps the Order ID and applies to a Limit order that keeps its price and does not increase its total quantity, and Amend or Replace amends when possible. In practice a replace-batch item that keeps the price and decreases newQtyScaled (5000 to 4500, 4500 to 4000), or keeps price and quantity unchanged, always returns REPLACED with a new order id; the old order becomes CANCELED with terminalReason ORDER_REPLACED, and GetBatchReplaceStatus also shows REPLACED. AMENDED was never returned. POST /v1/orders/modify with the same decrease returns AMENDED and keeps the id, but modify with unchanged price and quantity also returns REPLACED with a new id. The replace-batch reference defines AMENDED differently, as cancel-only without a successor with replacementOrderId zero, while its own response example shows AMENDED with replacementOrderId equal to oldOrderId. Is this by design, and in which case does replace-batch return AMENDED?

POST /v1/orders/replace-batch and POST /v1/orders/modify: the developer docs (Scaled Integers) say REST exposes decimal values as strings and REST clients do not need to decode *_scaled or *_ticks fields. newPriceTicks follows that and takes a decimal price string (1320 becomes price 1320), but newQtyScaled only accepts a JSON integer in pair scale (0.0045 ETH must be sent as 4500); the decimal string 0.0045 and the number 0.0045 are rejected with 400 cannot unmarshal ... of type int64. The fields of replace-batch items are not described on the reference page, only shown in the example.

POST /v1/orders/replace-batch response: acceptedTs is documented as a string (example 2025-01-01T00:00:00Z) but is returned as an object with seconds and nanos. Fields with a zero value are omitted: results[0] has no itemIndex, acceptedCount is missing when nothing is admitted, rejectedCount is missing when nothing is rejected. Is this by design?

POST /v1/orders/replace-batch results: for an unknown orderId and for an order of another pair oldOrderId comes back as 1 (zero id) instead of the orderId from the request, so a rejected item can only be matched by position. For CONFLICT_DUPLICATE_CLIENT_ORDER_ID the rejected item has replacementOrderId equal to oldOrderId, while the reference says zero for a rejection before assignment. Is this by design?

Addition to the modify ticket about an order of another pair: replace-batch behaves the same, an AVAX-USDT order sent with symbol ETH-USDT is rejected with UNKNOWN_SYMBOL.

Attached TP/SL prices are not validated. On ETH-USDT (tick 0.01) newAttachedRisk in replace-batch and attachedRisk in POST /v1/orders accept a takeProfit triggerPrice of 3500.005, and the leg trigger is created with 3500.005; a takeProfit at 1000 on a BUY order at 1350 is accepted as well. A standalone POST /v1/triggers on ETH-USDT with triggerPrice 3500.005 is rejected with PRICE_TICK_SIZE. Is this by design?

POST /v1/triggers: clientTriggerId is not marked required on the REST page (the ConnectRPC page says min 1 chars), and without it the API returns 400 VALIDATION_ERROR trigger.client_trigger_id must be at least 1 characters. No maximum length is documented. A clientTriggerId of 64 characters is accepted, 65 or more returns 503 UNAVAILABLE with a read_decode connection reset by peer message that contains an internal host and port, instead of a 400 validation error.

POST /v1/triggers with a clientTriggerId that already exists and a different body (other qty or other triggerPrice) returns a Cloudflare 502 Bad gateway HTML page instead of a JSON error such as CONFLICT_DUPLICATE_CLIENT_TRIGGER_ID; the original trigger stays unchanged. The same clientTriggerId with the same body correctly returns the original trigger. Related to the 502 on parallel DELETE of attached legs reported on 27.09, but here it is a single request.

GET /v1/triggers/id right after a successful POST /v1/triggers returned 404 NOT_FOUND in 3 of 10 attempts (200 after 0.3 s), and GET right after a DELETE that returned CANCELED showed ARMED in 6 of 10 attempts (CANCELED after 1 s). For orders the developer docs say GetOrder briefly waits server-side when an accepted order has not reached the read projection and returns a temporary unavailable error instead of NOT_FOUND. Is the trigger behavior by design?

GET /v1/triggers: the parentOrderId filter is ignored, a real parent id (base58 or numeric), a non-existent id and no filter return the same list; the same filter on ConnectRPC ListTriggers returns exactly the two legs of that parent and rejects a non-existent id. The status filter is documented as TriggerStatus enum names listed as CREATED, ARMED, RUNNING, COMPLETED, CANCELED, FAILED, PAUSED, but status=CANCELED returns 400 INVALID_TRIGGER_STATUS; only the ConnectRPC names such as STATUS_CANCELED work, comma-separated values too.

POST /v1/triggers ladder: postOnly is marked required on the REST page and optional on the ConnectRPC page; a ladder without it is accepted and the level orders are placed without post-only. Is this by design?

Addition to the ticket about scaled prices in the triggers reference: trailingDistanceTicks is described as a delta in 1e-9 quote-unit ticks, but it is parsed as a decimal price, as the developer docs say for REST: up to 9 fractional digits are accepted, 9223372036 is accepted and 9223372037 returns overflow (int64 divided by 1e9), so 1 means 1 USDT. qty is described as scaled by base_quantity_scale (example 100000) but is a decimal: qty 100 means 100 AVAX. TRAILING_DISTANCE_INVALID was never returned, a trailing distance of 9223372036 on AVAX-USDT at about 11.5 is accepted.


POST /v1/orders/replace-batch: в пользовательской документации (Manage orders) сказано, что правка на месте сохраняет Order ID и применяется к лимитному ордеру, у которого цена не меняется и общее количество не растёт, а режим Amend or Replace правит на месте, когда это возможно. На деле пункт replace-batch, который сохраняет цену и уменьшает newQtyScaled (5000 до 4500, 4500 до 4000) или оставляет цену и количество без изменений, всегда даёт REPLACED с новым id ордера; старый ордер становится CANCELED с terminalReason ORDER_REPLACED, GetBatchReplaceStatus тоже показывает REPLACED. AMENDED не пришёл ни разу. POST /v1/orders/modify с тем же уменьшением возвращает AMENDED и сохраняет id, но modify без изменения цены и количества тоже возвращает REPLACED с новым id. Справочник replace-batch определяет AMENDED иначе, как отмену без преемника с нулевым replacementOrderId, а пример ответа на той же странице показывает AMENDED с replacementOrderId, равным oldOrderId. Так задумано, и в каком случае replace-batch возвращает AMENDED?

POST /v1/orders/replace-batch и POST /v1/orders/modify: в документации для разработчиков (Scaled Integers) сказано, что REST отдаёт десятичные значения строками и REST-клиентам не нужно разбирать поля *_scaled и *_ticks. newPriceTicks этому следует и принимает десятичную цену строкой (1320 становится ценой 1320), но newQtyScaled принимает только целое JSON-число в масштабе пары (0.0045 ETH нужно отправлять как 4500); десятичная строка 0.0045 и число 0.0045 отклоняются с 400 cannot unmarshal ... of type int64. Поля items у replace-batch на странице справочника не описаны, они есть только в примере.

Ответ POST /v1/orders/replace-batch: acceptedTs в справочнике строка (пример 2025-01-01T00:00:00Z), а приходит объектом с seconds и nanos. Поля с нулевым значением пропускаются: у results[0] нет itemIndex, acceptedCount нет, когда ничего не принято, rejectedCount нет, когда ничего не отклонено. Так задумано?

results в POST /v1/orders/replace-batch: для несуществующего orderId и для ордера другой пары oldOrderId приходит как 1 (нулевой id), а не orderId из запроса, поэтому отклонённый пункт можно сопоставить только по позиции. При CONFLICT_DUPLICATE_CLIENT_ORDER_ID у отклонённого пункта replacementOrderId равен oldOrderId, хотя в справочнике для отказа до назначения указан ноль. Так задумано?

Дополнение к тикету про modify и ордер другой пары: replace-batch ведёт себя так же, ордер AVAX-USDT, отправленный с symbol ETH-USDT, отклоняется с UNKNOWN_SYMBOL.

Цены привязанных TP/SL не проверяются. На ETH-USDT (шаг 0.01) newAttachedRisk в replace-batch и attachedRisk в POST /v1/orders принимают takeProfit triggerPrice 3500.005, и триггер ноги создаётся с 3500.005; takeProfit 1000 у ордера BUY по 1350 тоже принимается. Отдельный POST /v1/triggers на ETH-USDT с triggerPrice 3500.005 отклоняется с PRICE_TICK_SIZE. Так задумано?

POST /v1/triggers: clientTriggerId на странице REST не помечен обязательным (на странице ConnectRPC указано min 1 chars), и без него API отвечает 400 VALIDATION_ERROR trigger.client_trigger_id must be at least 1 characters. Максимальная длина не указана. clientTriggerId длиной 64 символа принимается, 65 и больше даёт 503 UNAVAILABLE с сообщением read_decode connection reset by peer, в котором виден внутренний хост и порт, вместо ошибки валидации 400.

POST /v1/triggers с уже существующим clientTriggerId и другим телом (другой qty или другой triggerPrice) возвращает HTML-страницу Cloudflare 502 Bad gateway вместо JSON-ошибки вроде CONFLICT_DUPLICATE_CLIENT_TRIGGER_ID; исходный триггер не меняется. Тот же clientTriggerId с тем же телом правильно возвращает исходный триггер. Родственно 502 при параллельном DELETE привязанных ног, отправленному 27.09, но здесь это одиночный запрос.

GET /v1/triggers/id сразу после успешного POST /v1/triggers вернул 404 NOT_FOUND в 3 из 10 попыток (через 0.3 с — 200), а GET сразу после DELETE, вернувшего CANCELED, показал ARMED в 6 из 10 попыток (через 1 с — CANCELED). Поведение триггеров так задумано?

GET /v1/triggers: фильтр parentOrderId игнорируется, настоящий id родителя (base58 или числом), несуществующий id и запрос без фильтра возвращают один и тот же список; тот же фильтр в ConnectRPC ListTriggers возвращает ровно две ноги этого родителя, а несуществующий id отклоняет. Дополнение к тикету про scaled-цены в справочнике триггеров: trailingDistanceTicks описан как дельта в тиках 1e-9 quote-единиц, но читается как десятичная цена, как и сказано про REST в документации для разработчиков: принимается до 9 знаков после точки, 9223372036 принимается, а 9223372037 даёт overflow (int64, делённое на 1e9), то есть 1 означает 1 USDT. qty описан как масштабированный по base_quantity_scale (пример 100000), но это десятичное число: qty 100 означает 100 AVAX.
