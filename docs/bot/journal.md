## Что это

Грид-бот для спотовой биржи Polyester (тестнет), Python + asyncio, интерфейс —
Telegram Mini App. Автор — Snovin, не программист: объяснять решения по-русски,
давать команды PowerShell целиком, готовыми к вставке.

Стратегия описана в `final_strategy.md` (лежит в проекте с 2026-09-18);
`docs_strategy_review2.md` — один из трёх разборов. Старая папка
`Desktop/POLYESTER BOT` удалена 25.09 (в корзину), всё нужное перенесено:
ранние наброски и два других разбора (`project_structure.md`,
`Qwen_markdown_3.md`, `trading_logic1.md`) и заметка автора `добавления в
доки.txt` — в `archive/`; снимок документации Polyester от 10–11.09 (6 файлов,
10 МБ) — в `data/docs_snapshot_2026-09-10/` (в git не попадает), годится для
сравнения со свежими доками: так 24.09 нашли новые страницы. Она собрана из базовой логики и разборов трёх ИИ; числа в ней
названы стартовыми и неоптимизированными. Менять их только по накопленной
статистике. Правки после сверки с биржей — в её разделе 13.

Суть в одной фразе: сетка зарабатывает только в боковике, поэтому добавлено
определение режима рынка по свечам, а поверх него — аварийные стопы, которые
на индикаторы не смотрят вообще.

## Архитектура

Девять модулей в `core/`, каждый писался и проверялся отдельно:

- `config.py` — ВСЕ числовые параметры стратегии + машина состояний
  (9 состояний, карта допустимых переходов). Единственный источник правды.
- `api_client.py` — REST-клиент, подпись Ed25519, ретраи.
- `market_data.py` — свечи, публичные сделки, пульс рынка (цена последней
  сделки, сделок/час, оборот/час, возраст последней сделки), комиссии.
  Стакана и спреда НЕТ — см. ключевые решения.
- `indicators.py` — EMA, ATR, ADX, Donchian, фильтр аномальных свечей.
  Чистый Python, без numpy.
- `regime.py` — голосование 2 из 3 (Donchian + ADX + EMA), асимметричный
  hysteresis, вето старшего ТФ.
- `grid_engine.py` — геометрический шаг из четырёх полов, размер уровня через
  риск, нейтральный инвентарь, фильтр пары, условия входа. Только расчёт.
- `order_manager.py` — постановка, парная логика, частичные исполнения, пыль,
  flatten, сверка с биржей. Только исполнение.
- `risk.py` — два слоя: аварийный (каждый опрос) и советующий (на закрытии
  свечи). Только вердикты, ничего не исполняет.
- `process_manager.py` — два контура опроса, машина состояний, оркестрация.
- `scanner.py` — подбор пары (с 2026-09-19). Считает по каждой паре шаг,
  суточный путь и извилистость, ожидаемые циклы в день, размер уровня ТОЙ ЖЕ
  формулой, что и планировщик (включая уступку до `min_levels`), режим рынка
  и блокеры фильтра п.5; сортирует по метрике. Только чтение.
  CLI: `python -m core.scanner 31`.
- `client_factory.py` — выбор клиента биржи по `POLYESTER_CLIENT` (rest|sdk).

`bot.py` — Telegram + HTTP-роуты для вебаппки. `webapp/index.html` — интерфейс.

## Ключевые решения (не менять без обсуждения)

- **Шаг геометрический**, в долях цены. Арифметический давал разный процентный
  профит на разных уровнях и ломал комиссионный расчёт.
- **Комиссионный пол = 3 × (maker + maker)**, оба конца мейкерские, потому что
  вся сетка post-only. Если maker = 0 — пол берётся от taker как страховка.
- **`tp_price` хранится на уровне**, а не считается как `price + instance.step`.
  При геометрической сетке абсолютный шаг у каждого уровня свой.
- **Целевая доля базы 35–65 %.** Старые 15–85 % превращали грид у нижней
  границы в лонг на надежду.
- **Размер уровня считается по каждому buy-уровню отдельно**, не через среднюю
  цену входа: усреднение систематически занижает риск верхних уровней.
- **Стакана и спреда в коде нет вообще (с 2026-09-19).** Решение автора:
  стакан рисуется руками, уровни втыкают и убирают, полагаться на него нельзя.
  Живость пары определяется по публичным сделкам (`get_market_pulse`:
  сделок/час, оборот/час, возраст последней сделки), цена — по последней
  сделке. Спредовый пол шага и фильтры по спреду/глубине удалены, вместе с
  ними `spread_floor_mult` и `min_depth_*`. Не возвращать.
- **Аварийный слой не смотрит на индикаторы** и не ждёт подтверждений. Во время
  FLATTENING он молчит, иначе повторный вердикт слал бы второй market-ордер.
- **Пробой вверх проверяется раньше протухшей сетки.** В обратном порядке
  залипшая сетка на растущем рынке уходила в кэш вместо HOLD.
- **Риск-лимиты задаются только в `config.py`**, из интерфейса не редактируются.
  Они связаны с расчётом размера уровня, и правка одного без другого ломает
  математику.

## Грабли API (проверено на живой бирже)

- `get_orderbook` без параметра `depth` возвращал пустые bids/asks при живых
  bookSeq и ts (до 17.09). 18.09 в 18:20 UTC без `depth` пришёл полный стакан —
  починили. Глубину всё равно передаём всегда, вреда нет.
- `"timeframe"`, не `"interval"`. `"marketIoc"`, не `"market"` — в том числе
  в `preview_order`.
- `"CANCELED"` с одной L, как у биржи.
- `client_order_id` ограничен 36 символами — отсюда `short_instance_prefix()`.
- `get_order()` оборачивает ответ в ключ `"order"`.
- `str(0.00003)` даёт `"3e-05"`, API это отвергает — отсюда `format_decimal()`.
- Отменённый `client_order_id` повторно не принимается: при приостановке
  уровня создаётся копия с новым идентификатором.
- Свечи при отсутствии сделок рисуются с нулевым объёмом и совпадающими OHLC.
  Бывают выбросы на порядки (наблюдался хай 10 000 000 при цене 76 000) —
  ради них написан `filter_anomalous_candles`.

## Контракт API по документации (сверено 2026-09-17/18)

Прочитан весь раздел разработчика и REST-справочник (89 страниц скачаны и
разобраны). Живым прогоном НЕ подтверждено, если не сказано иначе.

Ордера и исполнение:
- Статусы ордера: `PENDING, PENDING_CANCEL, WORKING, FILLED, CANCELED, REJECTED`.
  У ордера есть `leavesQty`, `version` (растёт на каждое изменение — ключ для
  сверки), `terminalReason` (например `POST_ONLY_CROSS`, `USER_REQUEST`),
  `origin.scope` (`DIRECT | ATTACHED_RISK | STANDALONE_TRIGGER | SYSTEM`) и
  `origin.parentOrderId` у child-ордеров attachedRisk.
- Post-only только у `limitGtc`; пересекающая заявка отклоняется кодом
  `POST_ONLY_CROSS`, цена не сдвигается. STP по умолчанию `EXPIRE_MAKER`
  (снимается наш лежащий ордер целиком, входящий продолжает). Post-only
  проверяется раньше STP.
- Market = IOC с ценовой защитой: `maxSlippageBps` 1..10000 (или
  `maxSlippageTicks`, не оба), иначе дефолт пары `defaultMarketSlippageBpsSell`
  (0 = платформенный fallback). Может исполниться частично, остаток снимается.
  `clientRefPrice` + `maxClientRefDriftBps` → `STALE_QUOTE`.
- Размер: ровно одно из `baseQty` или `maxQuoteDebit` (последнее только для
  BUY market/limit IOC). `feeAsset` QUOTE (по умолчанию) или BASE (только BUY,
  если у пары `allowBuyFeeFromBase`). BUY с QUOTE резервирует notional + комиссию.
- Повтор `clientOrderId` → `CONFLICT_DUPLICATE_CLIENT_ORDER_ID` всегда, даже
  для отклонённого ордера (страница «Client order IDs» говорит обратное; верим
  справочнику и живому CONFLICT в `_submit_limit`).
- `cancel-all`: `symbols[]` (до 100), `side`, `dryRun`, `requestId` обязателен,
  стоит 10 единиц лимита; результат хранится 2 минуты. `cancel`: `orderId` или
  `clientOrderId`, `symbol` опционален; 404 при уборке = ордер уже ушёл.
- `modify`: `symbol`, `requestId`, `newQtyScaled` (ЦЕЛОЕ в масштабе пары),
  `newPrice`; `behavior AMEND_OR_REPLACE`. `batch` ≤ 20, `cancel-batch` и
  `replace-batch` ≤ 50, у всех `requestId`.
- `cancel-all-after`: `timeoutSec` 0 или 10..120, `requestId` обязателен,
  ответ `status ARMED|DISABLED`, `effectiveTimeoutSec`, `expiresAtTsNs`.
  Документация: продлевать задолго до истечения и ПРОВЕРЯТЬ status; не
  использовать account-wide cancel-all для уборки за процессом.
- `GET /v1/spot/orders/{id}`: `includeExecutionHistory=false` для опроса
  состояния, `true` — трейды с `fee` (десятичная строка в `feeAsset`),
  `isMaker`, `feeIsRebate`. `includeAttachedRiskState` даёт
  `attachedRisk.takeProfit.state` (`status NOT_CONFIGURED|CREATED|ARMED|
  RUNNING|COMPLETED|CANCELED|FAILED|PAUSED`, `childOrderId`, `triggerId`).
- `GET /v1/orders/open`: `limit` 1..1000, `pageToken`; `symbol` в справочнике
  показан JSON-массивом — живьём (18.09) массив даёт 400 UNKNOWN_SYMBOL, а
  обычная строка `symbol=BTC-USDT` работает. Ошибка справочника.
  `GET /v1/spot/trades` — наши исполнения.
- Балансы: `available` (уже без резерва), `reserved`, `trading`, `funding`,
  ревизии. Живой REST отдаёт десятичные строки; SDK — сырые u128 (scale 18).

Данные:
- Свечи: `limit` до 10000 (дефолт 500), newest-first, 7 полей
  `[ts, o, h, l, c, volBase, volQuote]`, `includeIncomplete` добавляет текущую.
- Стакан: `depth` — enum допустимых значений (по SDK: 1, 5, 10, 20, 50, 100,
  200, 500, 1000), без параметра живая биржа отдаёт пустоту.
- Spot config: статусы пары `ENABLED | DISABLED | CANCEL_ONLY | POST_ONLY |
  REDUCE_ONLY` (живая биржа отдаёт с префиксом `PAIR_STATUS_`), `symbolId`,
  `baseQuantityScale`, `defaultMarketSlippageBps*`, `maxClientRefDriftBps`,
  `allowBuyFeeFromBase`. Актив в `assets` — поле `asset`.
- Комиссии VIP 0: maker 0.1 % / taker 0.15 %; VIP 1 0.08/0.135; VIP 6
  0.02/0.07. Реферал −4 % к комиссии. `/v1/spot/fee-rates` — эффективные
  ставки по паре (`symbol`, `makerFeeRatePercent`, `takerFeeRatePercent`).

Доступ и лимиты:
- Подпись: `X-API-TIMESTAMP` в пределах ±10 с от времени сервера, иначе
  `TIMESTAMP_SKEW`; повтор того же подписанного запроса → `SIGNATURE_INVALID`.
  Клиент теперь берёт смещение из заголовка `Date` и переподписывает.
- 429: тело `rate_limit.retry_after_ms`, заголовки `Retry-After`,
  `RateLimit-*`. Торговля VIP 0: place 250/с (burst 500), cancel 500/с;
  cancel-all = 10 единиц, batch — 1/элемент. 503
  `RATE_LIMIT_AUTHORITY_UNAVAILABLE` — не отказ и не успех, сверять.
- Политика API-ключа/сабаккаунта может ограничить максимальный размер ордера
  и число открытых ордеров; ошибка придёт как permission-denied на create.
- Ежедневная раздача тестовых средств: `GET/POST /v1/trading/daily-claim` —
  только с сессией сайта, API-ключ не принимается. Забирать вручную на сайте.
- Realtime (приватные стримы ордеров/балансов) есть только через SDK
  (Centrifugo protobuf); REST-версия бота опрашивает.

## Подбор пары (с 2026-09-19)

Запрос автора: при открытии сетки бот должен сам просканировать пары и
предложить подходящую, а выбор оставить за человеком.

`core/scanner.py` + роут `GET /api/markets/scan?budget=30` (кэш 60 с) +
вебаппка: при открытии выбора пары ДЛЯ СЕТКИ список сортируется по метрике,
у лучшей значок «лучшая», под каждой парой строка «шаг · циклов/день · ~%/день»
или причина непригодности. Для ручного ордера подбор не показывается.

Метрика: `циклов_в_день × (шаг − 2 × maker)`, где циклов_в_день =
`суточный_путь / (2 × шаг)`, а суточный путь — сумма модулей приращений close
за 24 бара. Делитель 2 — потому что цикл это путь вниз к покупке и вверх к
парной продаже. Через ATR считать нельзя: когда шаг упирается в `vol_step`
(который сам из ATR), ATR в формуле сокращается и у всех пар выходит ровно
24 цикла — метрика вырождается. Рядом печатается извилистость
(`путь / смещение`): 1 = цена ушла по прямой (тренд, сетке плохо), больше =
пила. Это ОЦЕНКА СВЕРХУ: весь суточный путь считается полезным, хотя в тренде
цена не возвращается. Годится для сравнения пар между собой, не годится как
обещание доходности — так и подписано в интерфейсе.

Размер уровня сканер считает ТОЙ ЖЕ функцией, что планировщик
(`size_per_level_by_risk`), и так же уступает до `min_levels`, если не проходит
minNotional. Раньше он делил бюджет на число уровней и получалось, что сканер
обещает пару, на которой `check_entry` потом отказывает. В таблице сканера есть
и режим рынка по 1h — не блокер (меняется каждый час), но сетке нужен FLAT.

Важно про «дешёвые монеты выгоднее»: неверно. Доход = размер уровня × шаг в
процентах, цена монеты в формулу не входит. Значение имеют волатильность
(частота ступенек), комиссия (задаёт минимальный шаг), minNotional и то,
идут ли по паре сделки вообще.

## Экономия токенов (жёстко, с 2026-09-20)

20.09 за один день ушло 40 % недельного лимита. Разбор, что жгло, и правила
на будущее — они важнее удобства.

- **Правки только точечные, по уникальному якорю.** Переписывание файла
  скриптом (python-heredoc, sed по всему файлу) заставляет систему заново
  подать ВЕСЬ файл в контекст — сотни строк за одну правку. Это дало
  основную часть расхода. Скрипт оправдан только там, где точечная правка
  невозможна.
- **Не перечитывать файлы.** Нужен кусок — `grep` с `head`, а не чтение
  целиком. После своей правки файл не перечитывать: если бы она не легла,
  инструмент сказал бы.
- **Разведку по API не вести вручную.** Сверка биржи — `daily_probe.py`,
  один запуск, короткий вывод. Ходить по одному вызову за находкой нельзя.
- **Прогоны запускает автор**, присылает хвост вывода. Самому дёргать
  сканер, чек-энтри и бота — только когда без этого не ответить.
- **Отвечать коротко.** Развёрнутые разборы — по запросу.
- **Крупные куски по одному за сессию.** Не чинить четыре вещи подряд и не
  устраивать проверки вдогонку к разбору инцидента.
- **Перед любой правкой спрашивать.** Вопрос автора — это вопрос, а не
  задание чинить. Правило от 19.09, подтверждено 20.09.
